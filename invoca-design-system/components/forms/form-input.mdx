## What it is

`FormInput` is the one component that composes a complete labeled field: the control, its
[FieldLabel](/invoca-design-system/components/forms/field-label) (label text, optional marker, helper or error text, tooltip icon), and
the accessibility wiring that ties them together. A single `type` prop chooses which control
it renders.

**This is how you compose fields.** Assembling a field by hand from `FormControl`,
`FormLabel`, and a raw control is the retired path — see
[TITAN-FORM-01](/invoca-design-system/components/forms/form#constraints) and the `DoNotUse_*` stories on each type's page.

## Choose FormInput when

- You are adding any labeled field to a form. This is the default; the exceptions are
  narrow and listed below.

## Choose something else when

| If you need to… | Use | Why |
|---|---|---|
| Add a file-picking field | [FileUpload](/invoca-design-system/components/forms/file-upload) | `FormInput` has no `type` for file selection — see [Form / Composing a field](/invoca-design-system/components/forms/form#composing-a-field). |
| Add a date field | [DatePicker](/invoca-design-system/components/forms/date-picker) | Not one of `FormInput`'s types today; DatePicker composes its label directly. |
| Add a Switch | [Switch](/invoca-design-system/components/forms/switch) | `FormInput` has no `type` for a binary toggle — see [Switch's open issues](/invoca-design-system/components/forms/switch/open-issues). |
| Render a bare control with no label, helper, or error | The underlying control page | Rare — nearly every field in the product wants the full stack. |

## Types

Verified from `FormInput`'s source and its published Storybook stories, three of which are
explicit, named anti-patterns for hand-assembling the same field.

| `type` | Renders | Documented on | Anti-pattern story |
|---|---|---|---|
| `text` | Single- or multi-line text field | [Input](/invoca-design-system/components/forms/input) | `DoNotUse_RawTextField` |
| `select` | Select | [Select](/invoca-design-system/components/forms/select) | `DoNotUse_RawSelect` |
| `checkbox` | Single Checkbox, or a group when `options` is set | [Checkbox](/invoca-design-system/components/forms/checkbox) | `DoNotUse_RawCheckbox` |
| `radio` | Radio group | [Radio](/invoca-design-system/components/forms/radio) | Not published, but the same composition applies |
| `segmentedButton` | `ToggleButtonGroup` bound to a form value | Not documented as its own concept — overlaps with [ButtonGroup](/invoca-design-system/components/actions/button-group) ([open issue](/invoca-design-system/components/actions/button-group/open-issues)) | — |
| `custom` | Caller-supplied children inside the label/helper/error frame | — | — |

## Anatomy

| # | Part | Required |
|---|---|---|
| 1 | Field label | Yes — the visible label text, from [FieldLabel](/invoca-design-system/components/forms/field-label) |
| 2 | Optional marker | No |
| 3 | Tooltip icon on the label | No |
| 4 | The control itself | Yes — determined by `type` |
| 5 | Helper text | No — hidden when `error` is set |
| 6 | Error text | No — replaces helper text when the field is invalid |

## Edge and failure states

Owned by the control the `type` selects and by [FieldLabel](/invoca-design-system/components/forms/field-label#edge-and-failure-states).
A few behaviours are worth restating here because they are properties of `FormInput` itself:

| Situation | What happens |
|---|---|
| Both `helperText` and `error` are provided | Error wins. `helperText` is hidden. Confirmed directly in `FormInput`'s source: the `helperText` prop is documented as "Hidden when `error` is set (error wins)." |
| Field marked required | Enforced by the label; the marker rules are set on [FieldLabel](/invoca-design-system/components/forms/field-label#anatomy). |
| `type` set to a value the caller does not support | Runtime error from the type discriminator; not a graceful fallback. |

## Composition

Every field in the Forms category — [Input](/invoca-design-system/components/forms/input), [Select](/invoca-design-system/components/forms/select),
[Checkbox](/invoca-design-system/components/forms/checkbox), [Radio](/invoca-design-system/components/forms/radio) — composes through `FormInput`.
The shared label, group, and helper-text theming underneath comes from [Form](/invoca-design-system/components/forms/form).

The two composition boundaries worth naming:

- **`FormInput` composes the field.** Choose `type`, provide `label`, `helperText`, `error`,
  and the type's own props.
- **[FieldLabel](/invoca-design-system/components/forms/field-label) is the labeling concept `FormInput` renders.** It is not a
  component you compose by hand; every field label, helper text, and error text on a form
  goes through `FormInput`.

## Accessibility

`FormInput` wires the label, control, and helper-or-error text together — `for`/`id` (or
`aria-labelledby` for composed controls), `aria-describedby` for helper and error text, and
`aria-invalid="true"` on the control when `error` is set. Because this wiring is centralized,
a field composed through `FormInput` inherits it automatically; a field assembled by hand
from `FormControl` and a raw control does not.

**What this component does not handle:** deciding *when* a field is invalid, or moving focus
to the first invalid field on submit — both belong to
[Form validation](/invoca-design-system/patterns/form-validation).

## Constraints

| ID | Constraint | Rationale |
|---|---|---|
| **TITAN-FORM-01** | A labeled field is composed via `FormInput`, never by hand-assembling `FormControl` and `FormLabel`. | Both are exported from a module named `DeprecatedFormControls`, whose own JSDoc names `FormInput` as the replacement. |

See each type's page for its own constraints (for example, [TITAN-INPUT-08](/invoca-design-system/components/forms/input#constraints)
for `type="text"` and [TITAN-CHK-07](/invoca-design-system/components/forms/checkbox#constraints) for `type="checkbox"`).

## Why it works this way

**One composition, not per-type wiring.** If each field page owned its own label/helper/error
plumbing, the accessibility wiring would drift the first time one of them was edited alone.
Centralizing it in `FormInput` is what lets every field page stay silent about `aria-*`
wiring and helper-text theming.

**A `type` prop rather than a family of `FormTextInput` / `FormSelect` / `FormCheckbox`
components** because the composition around the control is the same in every case. The
control differs; the field around it does not.
